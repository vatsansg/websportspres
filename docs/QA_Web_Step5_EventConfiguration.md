| D-01 | TC-18 | `UserManagementComponent.removeUser()` originally used `window.confirm()` for the destructive-action prompt. Clicking "Remove" during this step's own live browser-automation testing triggered the native dialog, which **blocked the entire renderer** (screenshots, JS execution, and further input all timed out) until the tab was closed — a real, reproducible problem for anyone driving this page via CDP-based automation (and the same class of dialog the project already moved away from once before — Step 2's Create Event confirmation was deliberately built as an in-page panel instead of `alert()`, for the same reason). Not something a real person clicking in their own browser would notice, but a real regression risk for future automated QA passes, and inconsistent with the app's own established UX pattern. | Low (real people unaffected; automation/testability + UX-consistency issue) | **Fixed same day**: replaced with an inline two-step "Remove → Yes, Remove / Cancel" control (`confirmingRemoveId` signal), matching the project's no-native-dialogs precedent. Re-verify the new inline UI in the user's own testing pass. |
