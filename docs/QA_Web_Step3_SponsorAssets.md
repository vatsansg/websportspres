## Open defects / follow-ups

| ID | Linked test case | Description | Severity | Status |
|---|---|---|---|---|
| D-01 | TC-04 | Initial MP4 `tkhd` box parser had incorrect field offsets (used 84/96 instead of the correct 76/88 for version 0/1), returning garbage width/height (0, 25956) while duration parsing was already correct. Caught immediately by testing against real sample video files before any live deployment, not discovered live. | Medium (would have silently broken all video resolution validation) | **Fixed** before first deployment — corrected per the ISO/IEC 14496-12 `tkhd` field layout, re-verified against 4 real sample files (1080p and 4K variants) with correct results. |
| D-02 | TC-14 | Delete handler called `deleteSponsorAdFile` before `removeFromSponsorAdSequence`, but the sequence-removal logic depends on the blob still existing (via `listSponsorAdFiles`'s merged blob-listing+CSV view) to correctly detect whether the file was sequenced — so by the time it ran, the file was already gone from the listing and the removal was silently skipped every time. Caught via live testing (deleted a sequenced file, CSV was unchanged), initially misdiagnosed as still broken after a code fix due to a stale/pre-restart process (see D-04), then confirmed fixed with debug logging traced through the live log stream. | Medium — real, live bug; the deleted file's stale row would have persisted in `sponsorsequence.csv` referencing a filename that no longer exists in storage | **Fixed**: reordered the two calls (remove-from-sequence now runs first). Re-verified live via the debug-logging trace and a clean re-test — the CSV now correctly drops the deleted file's row. Debug logging was removed before final commit. |
| D-03 | TC-15 | Change log `filename` field capitalized "Inner"/"Outer" for New/Deleted entries (matching Web BRD Section 24's own example text) but used the real lowercase storage-folder casing for Updated (sequence-save) entries, derived from the actual blob path rather than built consistently. Caught by reviewing the live change-log CSV content after a full test sequence. | Low — cosmetic inconsistency in an audit-only field, no consumer currently reads this file (confirmed in Step 3 kickoff research) | **Fixed**: added a shared `changeLogPath()` helper used consistently by all three write sites (upload/delete/sequence-save), all now capitalize "Inner"/"Outer" per the BRD's own example. |
| D-04 | — | While testing the D-02 fix, the first re-test still showed the bug even though `az webapp deploy` + `az webapp restart` had both completed successfully and Kudu VFS confirmed the fixed file was on disk — a second, independent occurrence of the "deploy completes but the running process is still serving old code" issue first found in Step 2. A second restart-and-retest cycle (this time with debug logging to trace it conclusively) confirmed the fix was actually correct — the first negative result was the stale-process issue, not a real second bug. | Low — QA process risk, not an application bug | Reinforces the Step 2 lesson: always restart *and* allow a moment before trusting a "deploy completed" status for live re-verification; a flaky-looking live result should be re-traced with logging before concluding the code fix itself is wrong. |
